# SmartVoyage 个人项目讲解

## 项目定位与开场

可以这样介绍：

> 我基于已有的旅行多智能体代码，继续开发了 SmartVoyage 旅行规划与模拟预订平台。原来的重点是多 Agent 查询和生成回复，我补齐了用户与会话隔离、方案管理、可核对的报价、模拟订单及支付退款流程。系统将模型提供建议与确定性的交易规则分开：聊天负责解释和辅助，价格计算、预算检查、库存、订单状态和用户确认由程序控制。
>
> 项目支持不依赖外部服务的演示模式，也保留了 LangGraph、A2A 和 MCP 的联网 Agent 模式。默认演示不会调用大模型，联网模式也不会绕过方案确认自动下单。目前使用模拟供应商和模拟支付，适合展示工程能力，没有声称已经完成真实商业交易。

这是基于当前实现的讲解模板。使用前应亲自运行并理解对应代码。原有框架和依赖的来源应保留，不能把框架源码、已有底稿或 AI 辅助生成的全部代码描述为未经借助工具的原创。

## 业务问题

旅行规划容易出现信息分散、费用不透明、聊天答复不能保存或修改的问题。单纯生成一段行程文字，也不能说明价格有效、库存足够或订单已成立。

这个项目把用户旅程具体化为：

```text
账号登录 → 选择偏好 → 生成方案 → 修改并重新报价
→ 用户确认 → 占用模拟库存 → 待模拟支付
→ 模拟支付成功 → 取消并模拟退款 → 释放库存
```

旅行助手是辅助入口，不持有绕过业务规则的交易权限。

## 可以重点讲的五项实现

### 1. 从共享聊天对象改成独立会话

旧代码在 API 层复用全局 `ChatService`，只有一份记忆和最新 Trace。多人访问可能共享上下文。

现在账号、会话、消息、运行记录都有明确归属，服务端从登录 Cookie 确定用户，不能由客户端任意指定 `user_id`。每个资源都通过 `Store.owned()` 同时查询对象编号与所有者，越权返回404。

联网请求新建 `ChatService(persistent_memory=False)`，从 SQLite 加载该会话的记忆，完成后将新上下文写回。它不再调用旧版全局 MySQL 记忆表。通过数据库中的租约防止两个请求同时改写同一个会话，租约带随机标识，旧请求不能释放新请求的锁。

入口：`api/server.py`、`product/chat.py`、`product/store.py`。

### 2. 把行程与报价变成可保存的数据

用户填写城市、日期、天数、人数、预算和交通方式。`TripRequest` 验证边界；规则规划器从示例目录计算往返交通、逐晚住宿和模拟保障。

金额统一用整数分。住宿按每间最多2人计算，奇数人数向上取整；餐饮与市内交通是单独估算，不作为订单实付金额。预算检查会把两部分加在一起，避免“预订金额没有超预算，但旅行总开销明显超预算”的展示问题。

方案编辑后版本号加一，报价刷新，有效期15分钟。订单使用确定的方案版本，客户端不能直接传价格。

入口：`product/planning.py`、`product/booking.py`。

### 3. 做真实的模拟订单状态机

“模拟”指没有外部履约和资金流转，数据库里的订单、库存、事务和状态变化是真实执行的。

```text
pending_payment → confirmed → refunded
       ├───────→ cancelled
       └───────→ expired
```

下单要求显式确认，服务端再次检查方案归属、版本、有效期及目录价格。库存按产品和日期管理，以条件更新防止负库存；订单与库存写操作置于同一事务，后续任何一项失败都会整体回滚。

待支付订单过期后释放库存。模拟支付成功后取消则转为 `refunded`。取消和退款重复调用时不会重复释放库存。

入口：`product/booking.py`。

### 4. 处理重复提交与并发

下单接口要求 `Idempotency-Key`，使用“用户 + 请求编号”作为唯一约束，并保存方案编号及版本的指纹。同一请求重复提交返回原订单；同一编号换成另一个方案会被拒绝。

另有方案与订单的一对一约束，防止用户刷新页面后换请求编号导致重复占库存。新建一份方案才能开始新的预订。

SQLite 的 `BEGIN IMMEDIATE` 串行化写事务，配合 `available >= quantity` 条件更新。测试使用四条独立数据库连接同时下单，验证库存只有20个、每单6人时只能成功3单，不会超卖。

这证明当前事务逻辑在测试条件下成立，不代表已经测出生产 QPS 或分布式吞吐。

### 5. 让执行过程可查看、可验收

每次咨询保存独立 `run_id`、模式、执行状态、耗时和 Trace。规则演示明确显示零外部调用，不能把它描述为模型调用结果。订单、模拟支付、退款和会话清理写入当前用户的活动记录。

测试覆盖接口、所有者隔离、CSRF、报价过期、库存回滚、幂等和状态转换。浏览器验收真实点击表单和按钮，检查电脑和手机布局。

入口：`tests/test_product.py`、`scripts/browser_acceptance.py`。

## 原有多 Agent 部分怎么讲

联网调用链是：

```text
API → 当前用户会话上下文 → ChatService
→ LangGraph 意图识别和路由
→ 直接执行 / ReAct / Planner-Expert-Critic-Summary
→ A2A 专家服务 → MCP 工具 → 数据源
→ ExpertResult → 汇总 → 保存历史 Trace 与对话
```

- LangGraph 表达状态与分支，不等于每个专家都有独立 LangGraph。
- A2A 负责 Agent 之间的服务通信；MCP 负责工具暴露与调用。
- Planner、Critic 和 Summary 是中心编排中的模型角色，不应描述成全部独立部署的服务。
- `asyncio.gather` 组织专家任务，但旧链路仍有同步模型调用；不能只凭这行代码断言所有阶段都真正并行。
- Critic 给出修正建议，规则代码控制最多一轮修正。模型的评审不是预算或库存硬校验器。
- `ExpertResult` 区分成功、无数据、故障和缺参数，降低错误汇总风险；不等于数学意义上保证零幻觉。

## 3分钟演示顺序

1. 介绍这是个人项目，真实执行本地交易逻辑，外部产品与支付为模拟。
2. 注册账号，生成北京至成都三天一人的方案，展示费用拆分。
3. 修改为四天，展示版本号和报价变化。
4. 显式确认后创建订单，模拟支付，再模拟退款。
5. 切到活动记录，查看支付和退款事件。
6. 进入旅行助手询问方案，展示新建会话与历史 Trace。
7. 展示业务测试：越权拒绝、重复下单同一个订单、并发库存不为负。

## 简历可用表述

项目名称：**SmartVoyage 旅行规划与模拟预订平台（个人项目）**

项目介绍：围绕旅行方案生成、费用核对和模拟预订构建完整应用，支持独立用户会话、可编辑方案、订单状态管理及历史执行追踪；保留 LangGraph、A2A 和 MCP 多智能体查询链路。

职责可以按实际理解程度选用：

- 开发 FastAPI 业务接口和旅行工作台，实现账号登录、会话及资源归属校验、CSRF 防护和历史消息持久化。
- 设计版本化行程报价与模拟订单状态机，基于事务、条件库存更新和幂等请求实现下单、模拟支付、取消及退款。
- 改造多智能体入口的共享记忆问题，按会话注入独立上下文，保存每次运行的 Trace、状态及耗时。
- 编写业务验收和真实浏览器流程测试，验证越权访问、报价过期、重复提交、库存回滚及移动端体验。

不要补写未验证的“生产用户数”“日处理订单”“准确率提升百分比”“高可用架构”或“真实供应商出票”等成绩。

## 当前限制与下一步

当前应用存储适合本机或单机，不是多主机部署；账户没有邮件验证、找回密码和运营管理权限；库存没有真实供应商；模拟支付不包含第三方回调、对账或部分退款。没有真实天气或交通时刻时，会明确告知而不编造。

下一步最有价值的是选一个真实供应商沙箱完成搜索、重新报价、下单确认、取消及对账，然后迁移到生产数据库，建立固定问题集并分别评测工具成功率、事实依据、预算满足情况、延迟和模型成本。
