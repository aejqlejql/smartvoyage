# SmartVoyage 面试讲述与追问

本稿按当前源码与本次验收记录编写。项目定位为个人实战作品：本地业务闭环已验证，真实模型与供应商联调尚未完成。已有多智能体底稿、开源框架和辅助开发工具的来源应如实说明；下面的表述需要在自己能解释对应实现后使用。

## 一分钟项目介绍

> 我做的是 SmartVoyage 旅行规划与模拟预订平台，属于个人实战项目。我在现有旅行多智能体原型上补齐了账号和会话隔离、行程报价、库存和订单流程。联网咨询采用 LangGraph 控制意图识别、路由及协作，通过 A2A 调用天气、票务和行程专家，再通过 MCP 使用工具。价格、预算、库存和订单由确定性代码处理，用户确认后才能下单。我重点解决了共享记忆、重复提交、报价版本冲突和库存回滚等问题，并用接口和浏览器测试验证。当前供应商、支付与退款均为模拟，真实模型链路还没有完成端到端联调。

## 三分钟展开顺序

### 先讲业务问题

旅行助手只生成一段文字，用户仍然不知道费用怎么算、修改后怎么更新，以及预订是否真正成立。我希望把咨询建议延伸成可保存的方案、可核对的报价和可操作的模拟订单。

### 再讲总体结构

前端是无需构建的 HTML、CSS 和 JavaScript，后端使用 FastAPI。应用分成普通业务与联网咨询两条流程：业务模块负责输入校验、目录报价、库存和订单；咨询模块装配 LangGraph、专家注册表及工具服务。默认演示模式不调用大模型，便于稳定展示完整业务流程。

### 重点讲两个问题

第一个是会话隔离。原型复用全局 ChatService，存在多人共享记忆的风险。我改成从登录身份校验会话归属，按请求创建 Agent 实例并注入当前会话记忆。消息、上下文与运行记录都保存到应用库，同一会话用数据库租约避免并发覆盖。

第二个是订单一致性。方案有版本和15分钟报价有效期，下单前重新核对价格。通过用户与幂等编号唯一约束处理重复提交，库存按产品和日期做条件扣减。订单和全部库存写操作处于同一事务，某一项失败就整体回滚；取消和退款通过状态机保证库存只释放一次。

### 最后讲验证和边界

本次验收是73项测试通过、21项在线集成跳过，另有7组真实浏览器流程通过。其中新增业务测试36项，覆盖越权、CSRF、幂等、报价过期、并发下单、回滚及退款。联网适配成功/故障测试使用受控替身，不是实际模型评测。下一步优先打通自然语言到结构化方案，再接一个真实供应商沙箱，并建立固定问题集评测。

## 个人职责怎么说

可以围绕实际完成和理解的内容说：

1. 完善 FastAPI 业务接口及旅行工作台，补齐账号、独立会话和资源归属校验。
2. 实现版本化报价、预算检查、模拟订单状态机和事务库存。
3. 改造共享 Agent 记忆问题，接入按会话持久化的上下文与历史运行记录。
4. 编写自动化验收，覆盖重复提交、并发库存、越权及前端完整操作流程。

不要把 Planner、Critic、Summary 描述成全部由自己从零研发并独立部署的服务；它们在当前项目中是中心协作代码里的模型角色。不要把已有框架代码或底稿一概称为原创。

## 常见追问及口述答案

### 1. 为什么使用 LangGraph？

联网咨询有直接查询、分步执行、复杂协作、追问和错误处理等路径。LangGraph 用显式状态和条件边表达这些分支，使一次请求经过哪些步骤更容易追踪。当前使用它编排咨询工作流，订单和库存仍由普通业务代码控制。

代码：`core/graph/workflow.py`。

### 2. LangGraph 的节点具体有哪些？

主图包含 intent、route、plan、direct、react、collaborative、follow_up、error 和 finalize。Planner、专家、Critic 和 Summary 目前封装在 collaborative 节点内部，由 Python 代码组织调用，没有全部拆成独立图节点。

### 3. A2A 与 MCP 有什么区别？

A2A 用于主服务与专家 Agent 通信，专家可以接收任务、调用模型和工具并返回结果。MCP 用于暴露工具，例如天气、票务和旅游团检索。项目里主服务通过 A2A 找专家，专家再通过 MCP 使用具体查询能力。

代码：`agents/registry.py`、`a2a_server/`、`mcp_server/`。

### 4. 这里的多 Agent 是怎么协作的？

综合需求先由 Planner 拆任务，专家查询各自领域，Critic 检查缺失与冲突，必要时执行一轮修正，再由 Summary 汇总。修正最多取三个任务且只执行一轮。它是中心编排式协作，不能描述成多个 Agent 完全自主无限讨论。

代码：`core/collaboration_engine.py`。

### 5. 如何避免模型编造价格或天气？

专家结果统一为 success、no_data、error、input_required。没有数据、工具故障或缺参数时，优先保守回复；订单金额只能来自服务端目录报价，不能使用聊天生成的数字。这能降低风险，但还不能声称彻底消除模型幻觉。

代码：`contracts/expert_result.py`、`core/guardrails.py`、`product/planning.py`。

### 6. 多用户如何隔离？

服务器从登录 Cookie 确定用户，每个资源都同时按对象编号和 user_id 查询。联网请求新建 ChatService，关闭旧版全局 MySQL 记忆，只注入当前会话上下文，完成后写回。这样账号之间、会话之间都不会共用同一份可变记忆。

代码：`product/store.py`、`product/chat.py`。

### 7. 你做了 LangGraph 断点恢复吗？

当前做的是会话记忆、消息和运行记录的持久化，可以重启后继续对话。但没有配置 LangGraph checkpointer 来恢复正在执行的中间节点，所以不能说已经实现图执行断点续跑。进程中断后的进行中请求需要重新发起。

### 8. 如何防止重复下单？

接口要求 Idempotency-Key，用用户与请求编号做唯一约束，保存方案及版本的指纹。相同请求重试返回原订单，同一编号换方案会被拒绝。另有方案与订单的一对一约束，即使换一个编号也不会对同一方案再次占用库存。

代码：`product/booking.py`。

### 9. 如何防止超卖和部分扣库存？

库存更新要求 available 大于等于订购数量，并检查更新行数。交通、酒店等库存与订单写入放在同一个事务，一项失败整体回滚。当前基于 SQLite 写事务，已验证独立连接并发行为，但没有生产压测或分布式库存能力。

### 10. 报价为什么需要版本和有效期？

用户可能在两个标签页修改同一份方案，旧页面的价格不能直接用于下单。编辑会增加版本并刷新有效期，下单核对版本和过期时间，再按当前目录重新计算；发现变化就要求重新报价，订单则保存确认时的费用快照。

### 11. 退款为什么不会重复恢复库存？

订单有明确的状态转换。待支付取消进入 cancelled，已支付取消进入 refunded；已经取消、退款或过期时重复请求直接返回原状态。状态判断、库存释放和审计写入在事务中完成，因此不会因重试反复增加库存。

### 12. RAG 在哪里？

旅游团工具用 embedding 将查询变成向量，在 Milvus 做相似度搜索，并可按城市过滤，取回团名、天数、价格和产品亮点供专家使用。当前是产品语义检索，没有实现完整 BM25 混合检索、独立重排或大规模文档知识库治理。

代码：`mcp_server/mcp_trip_server.py`。

### 13. 为什么同时出现 SQLite、MySQL 和 Milvus？

职责不同。SQLite 保存本应用账号、会话、方案和订单；MySQL 是原有工具的结构化演示数据源；Milvus 用于旅游团语义检索。默认演示只需要 SQLite。多主机部署前需要迁移应用数据库和协调机制，不能把单机方案称为分布式系统。

### 14. 你如何证明项目有效？

当前能证明本地业务行为通过测试：包括归属校验、报价过期、重复下单、并发库存、事务回滚和浏览器操作。还不能给出模型准确率、生产 QPS 或商业转化率，因为没有完成对应评测。测试通过数是工程验收结果，不是 AI 效果指标。

### 15. 项目最大的不足是什么？

目前咨询和交易仍是两条流程，自然语言结果还没有统一转为可编辑的业务方案；产品、库存和支付也是模拟。下一步会先让模型输出受约束的需求草稿，经参数和预算规则校验后由用户确认，再对接真实供应商沙箱与评测集。

## 面试演示顺序

1. 明确介绍个人项目和模拟范围。
2. 生成默认三天方案，解释1610元预订金额与1970元旅行总预估。
3. 改为四天，展示报价和版本变化。
4. 确认创建订单，模拟支付并取消退款。
5. 查看活动记录，展示会话切换和执行 Trace。
6. 打开订单与测试代码，解释幂等、事务和隔离。

## 容易说错的表述

| 不准确说法 | 按当前实现应如何说 |
|---|---|
| 页面行程全部是大模型生成的 | 当前页面方案来自规则和模板，联网咨询另走 Agent 链路 |
| 所有业务都是 LangGraph 编排 | LangGraph 编排联网咨询，交易由业务服务执行 |
| 已经自动预订和支付 | 当前只有用户确认后的模拟订单与模拟支付 |
| 已实现完整断点恢复 | 已持久化会话和历史，未实现图中间节点恢复 |
| 有测试就说明模型效果好 | 业务测试与模型效果评测是不同证据 |
| 73项测试证明系统可商用 | 测试验证当前覆盖行为，21项在线集成仍跳过 |
| 已经支持高并发和生产高可用 | 目前是单机个人项目，尚无生产压测和高可用验证 |
